# Admin dashboard authentication

The dashboard at `/admin` uses a server-only username and bcrypt password hash.
There is no default account and no development bypass: every page and every
`/api/admin/*` endpoint stays locked until both variables are configured.

## Generate credentials privately

    npm run setup:admin

Run it in an interactive terminal. The password prompt disables terminal echo,
the password is never printed or written to a file, and the script outputs only
the two values to configure. It uses bcrypt cost 12.

## Variables to configure

| Variable | Where | Required | Notes |
| --- | --- | --- | --- |
| `ADMIN_USERNAME` | Server only (`.env.local` / Vercel) | Yes | 3-128 characters; letters, digits, `.`, `_` and `-`. Trimmed before comparison. |
| `ADMIN_PASSWORD_HASH` | Server only (`.env.local` / Vercel) | Yes | bcrypt hash generated by the script. Cost 10-15 is accepted. Never store the plaintext password. |
| `ADMIN_ENABLED` | Server only | No | Optional kill switch. `false` disables the dashboard even when credentials exist. |

Next.js expands `$` characters in `.env.local`, so use the escaped hash printed by
the script for local files (each `$` preceded by a backslash). Values entered in the
Vercel dashboard are literal: paste the raw hash there, without backslashes.

On Vercel: Project -> Settings -> Environment Variables. Add `ADMIN_USERNAME`
and `ADMIN_PASSWORD_HASH` for Production (and Preview if staff need preview
access), then redeploy. Do not add them to `NEXT_PUBLIC_*` and do not put them
in the repository.

## Session and request behaviour

- Login posts `username` and `password` to `/api/admin/login`. Failures return
  the same generic message for an unknown username and a wrong password.
- A successful login sets `dt_admin_session`, an HMAC-signed cookie containing
  only a username digest, issue time and 8-hour expiry. It is `HttpOnly`,
  `SameSite=Lax`, and `Secure` in deployed environments.
- `/api/admin/logout` clears the browser cookie. Sessions are stateless, so a
  copied cookie stays valid until its 8-hour expiry; rotating credentials
  invalidates all sessions.
- Login is limited to 5 attempts per 15 minutes per client IP (per instance).
- All state-changing admin requests must carry a same-origin `Origin` header.
- Proxy redirects unauthenticated page requests; a protected server layout
  verifies the signed session again before protected page content renders;
  every admin API re-verifies it at the data boundary.
- A broken or partial configuration fails closed: login, pages and APIs are
  unavailable rather than falling back to an open dashboard.

Rotating `ADMIN_PASSWORD_HASH` or `ADMIN_USERNAME` invalidates existing sessions.
